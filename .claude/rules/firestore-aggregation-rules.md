# 集計ルール: 明細が唯一のソース、計算結果をドキュメントに持たない

決定の経緯: https://github.com/bannzai/IdeaMemo/issues/188 の「技術スタック決定」コメント（[ADR 0001](../../documents/adr/0001-tech-stack.md) から参照）

## 原則

月次サマリードキュメント（materialized view）は作らない。派生データの二重管理になり、明細の編集・削除・重複マージ・計算対象からの除外（いずれも本アプリの仕様の核で経路が多い）のたびに整合性の悩みが生まれるため。持たなければ悩み自体が消える。

## 集計の実装方針

- **月次画面**: 一覧表示のために当月の明細をどうせ fetch するので、クライアント集計で収入・支出・カテゴリ内訳まで出す。snapshot listener でリアルタイム、オフラインキャッシュでも動く
- **長期グラフ（例: 3年の月次推移）**: Firestore ネイティブの集計クエリ `sum()` を「月 × 収入/支出」ぶん並列発行する。集計クエリの課金はインデックスエントリ 1,000 件走査 = 読み取り 1 回換算なので、ヘビーユーザーの全期間集計でもコスト・レイテンシとも問題にならない
- Firestore の集計クエリには GROUP BY がない・リアルタイム購読不可という制約があるが、上記の使い分け（画面 = クライアント集計、レンジ集計 = クエリ）で吸収する
- 将来本当に遅くなったら、そのときにサマリーを「明細から再計算可能なキャッシュ」として後付けする。いま持たない選択はその退路を塞がない

## 明細ドキュメントの必須クエリ用フィールド

明細ドキュメントには以下を持たせ、複合インデックスを張る。クライアント集計・集計クエリのどちらもこの絞り込みが前提:

- `yearMonth`（"2026-08" 形式）
- `type`（income / expense）
- 計算対象からの除外フラグ
